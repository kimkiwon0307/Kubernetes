# Kubernetes 프로젝트 학습

## 1장 2교시 — Docker Compose와 Kubernetes의 운영 차이

### 1. Docker Compose란?

Docker Compose는 여러 컨테이너를 하나의 YAML 파일로 정의하고 실행·관리하는 도구이다.

**주요 특징**
- `compose.yaml` 파일로 여러 서비스 관리
- 컨테이너, 네트워크, 볼륨 설정 통합
- 단일 서버 환경에 적합
- 재시작 정책 및 수동 확장 지원

### 2. Docker Compose와 Kubernetes 비교

| 구분 | Docker Compose | Kubernetes |
|---|---|---|
| 운영 환경 | 주로 단일 서버 | 다중 노드 클러스터 |
| 컨테이너 관리 | 서비스 단위 | Pod 및 Controller 기반 |
| 장애 복구 | 컨테이너 재시작 지원 | 컨테이너 재시작 및 Pod 재생성 |
| 서버 장애 | 다른 서버로 자동 재배치 불가 | 정상 Node에 새 Pod 생성 가능 |
| 확장 | `--scale`로 수동 확장 | 수동 확장 및 HPA 자동 확장 |
| 배포 | 컨테이너 재생성·갱신 | Rolling Update 및 Rollback |
| 복잡도 | 낮음 | 높음 |

### 3. Kubernetes 핵심 동작 원리

**Desired State (원하는 상태)**

관리자가 선언한 애플리케이션의 목표 상태를 의미한다.

**Reconciliation (상태 조정)**

Kubernetes가 실제 상태와 원하는 상태를 비교해 차이를 줄이는 과정이다.

예시:

```text
Desired State: Pod 3개
Current State: Pod 2개

→ ReplicaSet이 부족한 Pod 생성
→ Scheduler가 실행할 Node 선택
→ kubelet이 컨테이너 실행 관리
```

**주요 구성요소**

- **Deployment:** 애플리케이션 배포와 원하는 복제본 수 관리
- **ReplicaSet:** 지정된 Pod 개수 유지
- **Scheduler:** 새 Pod가 실행될 Node 선택
- **kubelet:** Node에서 Pod의 컨테이너 실행 상태 관리

### 4. 장애 발생 시 동작

**① 컨테이너 장애**

- Docker: Restart 정책에 따라 컨테이너 재시작 가능
- Kubernetes: 컨테이너 재시작 또는 Pod 교체 등으로 복구 시도

**② Worker Node 장애**

1. Kubernetes가 Node 이상 상태 감지
2. 장애 Node의 Pod를 제거 대상으로 처리
3. ReplicaSet이 대체 Pod 생성
4. Scheduler가 정상 Node 선택
5. 새로운 Pod 실행

※ 정상 Node에 CPU·메모리가 부족하거나 스케줄링 조건이 맞지 않으면 Pod가 `Pending` 상태에 머무를 수 있다.

※ Kubernetes의 자동 복구가 무조건적인 무중단 서비스를 보장하지는 않는다.

### 5. Docker Compose 주요 명령어

```bash
# 설정 파일 검증
docker compose config

# 서비스 실행
docker compose up -d

# 컨테이너 상태 확인
docker compose ps

# web 컨테이너 3개로 확장
docker compose up -d --scale web=3

# 서비스 종료 및 컨테이너 정리
docker compose down
```

**주요 옵션**
- `-d`: 백그라운드 실행
- `--scale web=3`: web 서비스의 컨테이너 수를 3개로 조정
- `restart: unless-stopped`: 수동 중지한 경우 등을 제외하고 컨테이너 자동 재시작

### 6. Kubernetes 도입 기준

**Docker 또는 Docker Compose가 적합한 경우**
- 서버 한 대에서 간단한 서비스 운영
- 컨테이너 수와 운영 복잡도가 적음
- 간단한 개발·테스트 환경

**Kubernetes 도입을 고려할 경우**
- 여러 Node에서 애플리케이션 운영
- Pod 자동 복구 및 재배치 필요
- 서비스 확장과 배포 자동화 필요
- 복잡한 애플리케이션 운영 및 관리

**핵심:** 컨테이너 수만으로 Kubernetes 도입 여부를 결정하지 않는다. 가용성, 확장성, 운영 비용, 관리 복잡도를 함께 고려한다.

### 7. 면접 핵심 질문

**Q1. Docker Compose와 Kubernetes의 차이는?**

Docker Compose는 주로 단일 서버에서 여러 컨테이너를 정의하고 관리하는 도구이다. Kubernetes는 여러 Node에서 컨테이너화된 애플리케이션의 배포, 복구, 확장 및 업데이트를 관리하는 오케스트레이션 플랫폼이다.

**Q2. Kubernetes에서 Worker Node가 장애를 일으키면?**

Kubernetes가 Node 장애를 감지하고, Deployment가 관리하는 Pod를 원하는 개수만큼 유지하도록 대체 Pod를 생성할 수 있다. Scheduler는 정상 Node에 새 Pod를 배치한다.

단, 정상 Node의 자원이 부족하면 복구가 실패하거나 지연될 수 있다.

**Q3. Pod가 Pending 상태인 이유는?**

CPU·메모리 부족, Node 배치 조건 불일치, 볼륨 관련 문제 등으로 Pod가 스케줄링되거나 실행되지 못하는 상황일 수 있다.

`kubectl describe pod`의 Events를 확인하여 원인을 분석한다.

**Q4. 서버 한 대에서 Spring Boot를 운영하는데 Kubernetes가 필요할까?**

반드시 필요하지는 않다. 간단한 서비스라면 Docker만으로 운영할 수 있고, 여러 컨테이너를 함께 관리한다면 Docker Compose가 적절할 수 있다.

Kubernetes는 다중 노드 운영, 자동 복구, 확장 및 배포 요구사항이 클 때 검토한다.

### 핵심 요약

- **Docker Compose:** 여러 컨테이너를 간편하게 정의하고 관리
- **Kubernetes:** 클러스터 기반 애플리케이션 운영 자동화
- **Desired State:** 관리자가 원하는 상태
- **Reconciliation:** 원하는 상태를 유지하기 위한 지속적인 조정
- **Self-Healing:** 장애 발생 시 컨테이너 재시작이나 대체 Pod 생성
- **Scheduling:** 적절한 Node에 Pod 배치
- **기술 선택 기준:** 서비스 규모뿐 아니라 가용성, 운영 복잡도, 확장 요구사항까지 고려
