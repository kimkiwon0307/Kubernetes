# Kubernetes 프로젝트 학습

## 2장 1교시 — Kubernetes 아키텍처와 내부 동작 원리

### 1. Kubernetes Cluster 구조

Kubernetes Cluster는 컨테이너화된 애플리케이션을 배포하고 관리하는 환경이다.

크게 두 부분으로 구성된다.

- **Control Plane:** 클러스터 상태 관리 및 작업 조율
- **Worker Node:** 실제 Pod와 컨테이너 실행

### 2. Control Plane 주요 구성요소

| 구성요소 | 역할 |
|---|---|
| kube-apiserver | API 요청 처리, 인증·인가 및 리소스 관리 |
| etcd | Kubernetes 클러스터 상태 데이터 저장 |
| kube-scheduler | Pod가 실행될 Node 선택 |
| kube-controller-manager | 원하는 상태를 유지하도록 컨트롤러 실행 |
| cloud-controller-manager | 클라우드 인프라와 연동 (선택) |

**핵심 개념**
- API Server는 Kubernetes 관리 요청의 중심이다.
- etcd는 클러스터 상태를 저장하는 키-값 저장소이다.
- Scheduler는 Pod를 직접 실행하지 않고 실행할 Node만 선택한다.
- Controller는 Desired State와 Current State의 차이를 줄이도록 동작한다.

### 3. Worker Node 주요 구성요소

| 구성요소 | 역할 |
|---|---|
| kubelet | Node에서 Pod의 실행 상태 관리 |
| Container Runtime | 실제 컨테이너 생성 및 실행 |
| kube-proxy | Service 트래픽 전달을 위한 네트워크 규칙 관리 (선택) |
| CNI Plugin | Pod 네트워크 구성 및 연결 |

**핵심 차이**

- **Scheduler:** Pod 실행 위치 결정
- **kubelet:** Pod 실행 관리
- **Container Runtime:** 실제 컨테이너 실행

### 4. Pod 생성 내부 동작 과정

Deployment에 `replicas: 3`을 지정했다고 가정한다.

```text
관리자 (kubectl)
    ↓
API Server
    ↓
etcd (Deployment 상태 저장)
    ↓
Deployment Controller
    ↓
ReplicaSet Controller
    ↓
Pod 3개 생성
    ↓
Scheduler (Node 선택)
    ↓
Worker Node의 kubelet
    ↓
Container Runtime
    ↓
컨테이너 실행
```

※ 위 흐름은 개념 이해를 위한 논리적 순서이다. 실제 Controller와 Scheduler는 API Server를 통해 리소스를 관찰하고 변경한다.

**핵심:** Controller가 원하는 Pod 수를 유지하고, Scheduler가 배치할 Node를 결정하며, kubelet과 Container Runtime이 실행을 담당한다.

### 5. 장애 발생 시 동작

**① 컨테이너가 비정상 종료된 경우**

```text
컨테이너 종료
    ↓
kubelet이 재시작 정책 확인
    ↓
Container Runtime에 재실행 요청
    ↓
기존 Pod에서 컨테이너 재시작
```

- 일반적인 Deployment Pod의 재시작 정책은 `Always`이다.
- 컨테이너 재시작 시 반드시 새로운 Pod가 생성되는 것은 아니다.

**② Deployment가 관리하는 Pod가 삭제된 경우**

```text
Pod 삭제
    ↓
ReplicaSet Controller가 부족한 Pod 확인
    ↓
새 Pod 생성
    ↓
Scheduler가 Node 선택
    ↓
kubelet → Container Runtime
    ↓
새 Pod의 컨테이너 실행
```

- 정상적인 클러스터와 충분한 자원이 있다는 전제에서 복구할 수 있다.
- Node 자원 부족이나 스케줄링 제약이 있으면 Pod가 `Pending` 상태에 머무를 수 있다.

### 6. 기본 확인 명령어

```bash
# 클러스터 정보 확인
kubectl cluster-info

# Node 목록 확인
kubectl get nodes -o wide

# 모든 네임스페이스의 Pod 확인
kubectl get pods -A

# Kubernetes 시스템 Pod 확인
kubectl get pods -n kube-system

# Pod 상세 상태 및 이벤트 확인
kubectl describe pod <pod-name>

# 클러스터 이벤트 확인
kubectl get events -A
```

### 7. 면접 핵심 질문 및 답변

**Q1. Control Plane과 Worker Node의 차이는?**

Control Plane은 클러스터의 상태를 관리하고 작업을 조율한다. Worker Node는 kubelet과 Container Runtime을 통해 실제 애플리케이션 컨테이너를 실행한다.

**Q2. Kubernetes에서 Pod가 생성되는 과정은?**

API Server가 Deployment 생성 요청을 처리하고 etcd에 상태를 저장한다. Controller가 ReplicaSet과 Pod를 생성하도록 관리하고, Scheduler가 Node를 선택한다. 이후 kubelet이 Container Runtime을 통해 컨테이너를 실행하도록 관리한다.

**Q3. Scheduler와 kubelet의 차이는?**

Scheduler는 Pod를 실행할 Node를 선택하고, kubelet은 해당 Node에서 Pod의 컨테이너가 실행되도록 관리한다.

**Q4. 컨테이너 장애와 Pod 삭제 시 복구 방식은?**

컨테이너가 종료되면 kubelet이 재시작 정책에 따라 기존 Pod에서 컨테이너를 재시작한다. Deployment가 관리하는 Pod가 삭제되면 ReplicaSet Controller가 대체 Pod를 생성하고 Scheduler가 Node를 선택한다.

**Q5. API Server에 장애가 발생하면 기존 Pod도 모두 종료되는가?**

반드시 그렇지는 않다. 이미 실행 중인 컨테이너는 계속 동작할 수 있지만, 새로운 API 요청과 클러스터 상태 관리 작업에는 문제가 발생할 수 있다.

### 핵심 요약

- **API Server:** 요청 처리
- **etcd:** 클러스터 상태 저장
- **Controller Manager:** 원하는 상태 유지
- **Scheduler:** Pod 실행 Node 선택
- **kubelet:** Node에서 Pod 실행 관리
- **Container Runtime:** 실제 컨테이너 실행

**Pod 생성 핵심 흐름**

`API Server → etcd → Controller → Scheduler → kubelet → Container Runtime`

**장애 복구 핵심 차이**

- 컨테이너 종료 → kubelet이 컨테이너 재시작 관리
- Pod 삭제 → ReplicaSet Controller가 대체 Pod 생성
